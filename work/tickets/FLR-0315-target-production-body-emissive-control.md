## Objective

Extend the existing opt-in emissive diagnostic so it targets the production
Sequoia body material `PaintColor`, not merely the first renderable material
(`Glass`). Use the Mac persistent Devtool source and official update-recipe
flow to generate the patch; then build and run the image on the Mini PC.
This is a diagnostic visibility control, not a product lighting fix.

## Success criteria

- Source edit is made only in the persistent Mac Devtool source.
- The patch is generated by Devtool from a committed source change and added
  to `meta-fluorite-trial`; no generated patch body is hand-edited.
- Mini bundle transfer, `do_patch`, component compile, full image, and QMP
  runtime all pass with hashes recorded.
- Runtime proves whether `PaintColor` emissive output produces native pixels
  while HUD and frame recovery remain active.
- QMP teardown and residual cleanup pass.

## Facts / hypotheses / UNKNOWN

### Facts

- FLR-0314 applied the current emissive override to `Glass` entity 352 and
  produced no native pixels.
- FLR-0312 identifies body entity 336 with material instance `PaintColor`.
- The current source gates the override on one global-applied flag and the
  first primitive, so it never reaches `PaintColor` in the observed order.

### Hypotheses

1. Applying emissive to `PaintColor` produces magenta body pixels, proving the
   target/camera/frame path and isolating the remaining issue to lit material
   evaluation.
2. `PaintColor` emissive still produces no pixels, falsifying the light-only
   explanation and moving the boundary to target/renderer/culling.

### UNKNOWN

- Whether `PaintColor` exposes an `emissiveFactor` parameter in this exact
  image after the source change.
- Whether one frame is sufficient before the FEngine fault.
