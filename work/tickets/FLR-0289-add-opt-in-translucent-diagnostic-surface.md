# FLR-0289 — add an opt-in translucent diagnostic surface

- Status: Waiting
- Priority: High
- Owner: diagnostic surface blend contract / production light A/B
- Created: 2026-09-25
- Predecessor: [FLR-0288](FLR-0288-test-production-light-attachment-in-diagnostic-scene.md)
- Working log: `work/logs/2026-09-25-flr0289.md`

## Objective

Add one opt-in environment control that keeps the diagnostic scene translucent
instead of forcing opaque. Use it to compare production Sequoia light output
with the proven HUD composition path. The default diagnostic and production
contracts must remain unchanged.

## Acceptance gate

After the official Devtool patch and Mini build, one QMP-only 1280x800 frame
with the opt-in control must show the HUD and a measurable native Sequoia ROI.
The runtime must prove diagnostic light attachment, model/material setup,
translucent blend, draw/present, and clean QMP teardown.

## Facts

- FLR-0286 proves a self-made LIT fixture plus explicit SUN light composes with
  the HUD.
- FLR-0287 proves production Sequoia model/material/camera/draw setup but a
  completely black native ROI while the default scene remains translucent.
- FLR-0288 proves 13 production lights reach the diagnostic scene, but the
  diagnostic path forces `blend=0` and hides the HUD.
- Source inspection identifies two diagnostic-only forced-opaque assignments:
  setup-time scene selection and the per-frame diagnostic-scene branch.

## Hypotheses

1. Preserving `blend=1` in the diagnostic scene will restore HUD composition
   and reveal whether the attached production lights change Sequoia pixels.
2. If the native ROI remains black with translucent composition, the next
   boundary is model material input or target draw output, not light ownership.

## Verification plan

- Edit the persistent Mac Devtool source, commit the source change, and use
  the deterministic component rebase/update-recipe flow to generate exactly one
  official patch in `meta-fluorite-trial`.
- Transfer the layer commit by bundle to the existing Mini receiver and run
  `do_patch`, `do_compile`, and the full image build progressively.
- Run one QEMU with the opt-in translucent diagnostic control, capture the
  bounded guest log before teardown, and retain QMP screenshot/video/ROI
  analysis.
- Do not combine SHM, opaque-surface, culling, or compositor-owner controls.

## Unknowns

- Whether translucency alone exposes production Sequoia pixels.
- Whether the production material's base color/light response is visible once
  the HUD is no longer covered.

### Decision

The opt-in blend fix removed the explicit opaque assignment but did not
restore HUD composition or colored Sequoia output. The renderer's existing
clear color is transparent `(0,0,0,0)`, so the next boundary is native surface
alpha/Wayland stacking or target import, not the light API. FLR-0289 is
Waiting; FLR-0290 owns bounded surface evidence. Default production behavior
remains unchanged.
