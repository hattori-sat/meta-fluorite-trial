# FLR-0272 — diagnose production asset/Scene loading OOM

- Status: Done
- Priority: High
- Owner: production asset lifecycle / Scene ownership
- Created: 2026-09-24
- Predecessor: [FLR-0252](FLR-0252-verify-production-planetarium-3d.md)

## Objective

Identify and correct the first production asset/Scene lifecycle condition that
causes `flutter-auto` to exhaust the current guest memory budget before a
stable Planetarium/Sequoia frame and QMP input transition can be verified.
The result must preserve the established self-made 2D+3D control and must not
silently substitute the fixture for the production route.

## Acceptance criteria

- Source inspection identifies the ownership and repetition boundary for model
  selection, asset load, Scene insertion, and cleanup.
- A bounded runtime run completes without guest OOM and without an unbounded
  model/Scene-add count.
- QMP proves a stable 2D frame and a production 3D ROI with actual chromatic
  pixels, or the first remaining boundary is explicitly isolated.
- Only after runtime health is restored, QMP input proves the Scenes action and
  Planetarium/Sequoia transition or records the next missing callback boundary.
- Any source change uses Mac persistent Devtool source commit → official patch
  generation → layer commit → Mini bundle → authoritative do_patch/compile/
  image/runtime verification.

## Initial evidence — Run 0294

- Current e876 production baseline reached ten asset-ready records,
  `MODEL_SELECTED=60`, `SCENE_ADD_DONE=55`, four draw submits, and five queue
  presents.
- `flutter-auto` was killed by the guest OOM killer at approximately 346.8 s.
- QMP initially showed the 2D HUD and a transient colored production ROI; the
  settled frame became white/black and did not prove stable 3D.
- Input was intentionally not attempted after the application died.
- Full evidence is recorded in
  [the FLR-0252 log](../logs/2026-09-24-flr0252.md).

## Verification plan

1. Inspect the current source loop and object ownership for repeated model
   selection, Scene insertion, and missing cleanup.
2. Compare at least two explanations: repeated retained instances versus one
   oversized/duplicated asset load.
3. Add only bounded diagnostics first if ownership is not statically clear.
4. If a fix is justified, generate it through the Mac Devtool lifecycle and
   verify it on Mini before rerunning QEMU.

## Current boundary — 2026-09-24

The bounded model scan now keeps the guest alive long enough to separate the
asset-lifecycle problem from the camera problem. Runs 0295–0299 recorded one
bounded production load window, one secondary model insertion, draw/present
activity, and clean QMP teardown. The QMP production ROI still had zero
chromatic pixels, so this is not yet 3D success.

Static source inspection then found a direct contract mismatch:

- The Dart patch stack places the first camera in `scene["camera"]` and omits
  root `cameras`.
- The current native `SceneTextDeserializer::DeserializeSceneLevel()` handles
  lights, skybox, and indirect light, but does not handle `camera`.
- The native root-level `cameras` path constructs `EntityObject`, `Transform`,
  and `Camera`, then `setUpEntities()` initializes the camera for
  `ViewTargetSystem`.
- Runtime 0299 showed model selection and Scene insertion, while the actual
  camera marker lines were absent and the effective camera remained
  `(0,0,0)`.

The first correction therefore restores the native-supported root `cameras`
payload and Dart camera initialization. This is an API-alignment correction,
not a fixture substitution and not yet proof that Wayland composition is fixed.
