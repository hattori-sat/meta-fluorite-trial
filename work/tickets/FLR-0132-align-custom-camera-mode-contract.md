## Work unit

Align the Dart camera payload and the native Filament camera-manipulator API
for the custom `INERTIA_AND_GESTURES` mode. Use the existing Mac Devtool source
workspace to make one minimal source change, generate the official untouched
patch, register it in `meta-fluorite-trial`, commit the layer, transfer the
bundle to the fixed Mini receiver, and run the progressive BitBake gates. Then
run one clean QEMU validation with a conditional single-process launch and
QMP-only visual evidence.

This ticket does not change Shape geometry, materials, lighting, blend mode,
Wayland stacking, or QEMU profile.

## Problem

The Dart package serializes `mode: INERTIA_AND_GESTURES`. The Mini source
recognizes that value as a custom mode, but the `Camera` constructor does not
assign a valid Filament `mode_` in that branch. `CameraManager::updateCamera`
then passes `cameraInfo->mode_` to the manipulator builder before
`setPrimaryCamera()` applies the custom look-at. The relation is API-visible and
must be corrected or falsified before further 3D conclusions are drawn.

## Success criteria

- The source change is made only in the fixed Mac Devtool workspace and the
  layer patch is generated by the documented Yocto Devtool flow; no patch body
  is hand-edited.
- The canonical layer commit and exact Git bundle tip are recorded; Mini
  `do_patch`, `do_compile`, and full image build pass in the fixed build/TMPDIR.
- The QEMU run uses the exact built image, one `flutter-auto`, one negotiated
  QMP teardown, and no residual target processes or sockets.
- Runtime evidence records camera receive/apply, Shape readiness, target/draw
  boundary markers, Vulkan submit/present, and QMP-only pixels.
- The fixed 3D region either contains the self-created Dart geometry or the
  evidence falsifies this camera-contract hypothesis and opens the next
  boundary as a new ticket.

## Facts

- Dart `Camera.toJson()` emits `INERTIA_AND_GESTURES`, target position, up
  vector, and flight-start position.
- Native `Camera` maps `INERTIA_AND_GESTURES` to a custom mode but does not
  assign `mode_` in the same branch.
- `CameraManager::updateCameraManipulator()` calls
  `manipulatorBuilder.build(cameraInfo->mode_)` for every camera update.
- FLR-0130 proved the camera message receiver and replacement call, but its
  fixed QMP 3D region remained black.
- FLR-0131 did not classify Shape-to-Draw because its launch procedure allowed
  a Wayland `agl_shell` collision and repeated frame skips.
- The first Mini `do_patch` attempt failed before compilation because the
  generated patch was registered without `;patchdir=ivi-homescreen-plugins`.
  Quilt reported `can't find file to patch` at the top-level flutter-auto
  source root. The registration was corrected and the progressive gates were
  rerun successfully.
- The clean current-source QEMU run reached `FLR0026_SHAPE_READY`,
  `FLUORITE_DESERIALIZED_CAMERA_RECEIVED`, and
  `FLUORITE_DESERIALIZED_CAMERA_APPLIED`. It did not report the historical
  `agl_shell extension already in use` collision and reported no coredump.
- The same run repeatedly reported
  `FLR0026_FRAME_FENCE_WAIT_LINKED linked=false` followed by
  `FLR0026_FRAME_SKIP_STATUS status=1`. It did not report
  `FLR0026_TARGET_RENDER_PASS_BEGIN`, `FLR0026_TARGET_DRAW`,
  `FLR0026_TARGET_DRAW2`, or a valid ViewTarget present marker.
- QMP-only analysis of the fixed 3D region `[300,250,620,400]` found zero
  changed pixels, zero edge pixels, zero chroma, and luma `[0,0]`; the region
  was uniformly black. QMP video contained eight frames and teardown was clean.

## Inferences

- The Dart/native camera contract was internally inconsistent for the custom
  mode and could make the manipulator input undefined before the look-at was
  applied. The Devtool-generated base-mode initialization corrected that API
  contract, but the QMP visual gate still failed.
- The smallest testable countermeasure is to retain the custom feature mode
  while assigning the normal Filament base manipulator mode expected by the
  builder (currently ORBIT), matching the native default-camera path.
- The first build failure is a layer registration-path defect, not evidence
  against the source API change. The existing `0239` registration provides the
  correct `patchdir` convention.
