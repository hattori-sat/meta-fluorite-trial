# FLR-0275 — isolate production payload visibility after camera correction

- Status: Done
- Priority: High
- Owner: production model / shape / material / native scene attachment roles
- Depends on: [FLR-0274](FLR-0274-diagnose-production-model-material-visibility.md)
- Working log: `work/logs/2026-09-24-flr0275.md`

## Problem

FLR-0274 proved that the startup camera was incorrectly selected, but the
corrected local camera still produces zero chromatic production pixels. The
next task must separate production payload visibility from the known-good
native fixture without changing the shared QEMU/Wayland surface contract.

## Facts

- The corrected authoritative runtime reports `camera_pos=(5,0,-5)`.
- Production asset load, secondary Scene insertion, draw submit/end, and queue
  present are positive.
- The same image's native fixture control produces colored QMP pixels.
- The corrected production QMP ROI remains `chromatic_pixels=0` and
  `max_chroma=4`.
- Existing diagnostic controls can bound model loading, environment/lights,
  and shape stages; these controls must be interpreted with their composition
  side effects.

## Hypotheses

1. The production model/shape payload is present but its transform or camera
   contract does not place visible geometry in the local view.
2. The production material/texture path produces the grayscale native surface
   even after camera selection.
3. UNKNOWN: production Scene attachment differs from the native fixture path
   after the Dart payload crosses the method channel.

## Success criteria

- Run one bounded A/B that keeps the corrected local camera and compares the
  smallest production payload stages.
- Preserve QMP still/video hashes and only the relevant runtime markers.
- Identify the first remaining zero boundary, or record UNKNOWN with the next
  smallest discriminator.
- Do not add a new patch until the source/runtime boundary is measured.

## Non-goals

- Do not revert the valid `0091` camera/route correction.
- Do not redesign Wayland/QMP composition while the fixture remains positive.
- Do not create a new build directory, TMPDIR, container, or QEMU instance.

## Verification plan

1. Reuse the fixed image and corrected local camera.
2. Run the smallest production payload A/B with one QMP instance.
3. Compare model/shape/material/attachment markers and ROI color metrics.
4. Only after the first differing boundary is known, create a Mac Devtool
   source change and repeat the canonical Mini bundle/build/runtime loop.

## Result

The A/B did not produce a valid payload-visibility verdict because the guest
application was killed by the kernel OOM killer before the QMP capture. The
runtime did prove that the current `0278` scene-stage controls reach shape
creation and the corrected camera, but the requested model-load skip was not
present in the current binary. Static inspection of `0278` shows
`setUpLoadingModels()` is unconditional; the current environment controls are
split into `FLR0026_NATIVE_SKIP_SKYBOX` and
`FLR0026_NATIVE_SKIP_INDIRECT_LIGHT`. Therefore the previous launch command
used stale control names and was not a valid shape-only experiment.

This ticket is closed as a diagnostic boundary, not as a 3D success. FLR-0276
owns restoring a bounded model-payload control against the current source
baseline.
