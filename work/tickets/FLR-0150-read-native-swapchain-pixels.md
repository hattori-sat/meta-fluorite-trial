## Facts

- FLR-0149 proved the native fixture emits `draw2` with 36 indices and one
  instance into a valid `swapchain=true extent=1280x800` target.
- RenderPass execute returns and queue-present returns `result=0`, but QMP
  remains uniform black in `[300,250,620,400]`.
- The existing target-content probe is limited to non-swapchain
  `1280x800` `VK_FORMAT_R16G16B16A16_SFLOAT` targets, so it cannot observe
  the fixture's `color_format=44` swapchain image.
- The existing `VulkanReadPixels::run` API already transitions a color image
  to `TRANSFER_SRC`, copies it into a host-visible staging buffer, restores
  the prior layout, and invokes a completion callback. The diagnostic must
  use the actual swapchain format and a bounded candidate region.
- Mini `filament-vk:do_patch`, `do_compile`, and the full
  `agl-ivi-image-flutter` build all passed from the same fixed build and
  TMPDIR. The image rootfs SHA-256 is
  `1b71c5614c0252dfaa7af459d1451b1130b05fa0d8bb47919ab11f20b3281b14`.
- The first QEMU host-side analysis attempt was rejected before a rendering
  verdict because the pre-app QMP frame was `720x400` while the fixed
  candidate region assumed `1280x800`. QMP quit and process cleanup still
  passed. The rerun measured the actual post-launch `1280x800` frame and used
  the bounded candidate region `[300,250,620,400]`.
- The rerun's serial evidence recorded a valid native resource contract
  (`entity=6`, one primitive, material connected, `vertex_count=8`,
  `index_count=36`), effective camera `(0,0,5)` looking at the origin,
  viewport `1280x800`, real `draw2`, RenderPass return, and queue present
  result `0`.
- The swapchain readback completed for the actual `1280x800` B8G8R8A8 target,
  but returned `nonzero_pixels=0`, `chromatic_pixels=0`, `byte_sum=0`, and
  `max_rgb_byte=0` for all `248000` candidate pixels. The paired QMP-only
  post-launch frame independently returned `0/248000`, `luma_range=[0,0]`,
  and dominant color `(0,0,0)`.
- Six QMP video frames were captured in the same run; their SHA-256 values
  are distinct. QMP quit was accepted and cleanup ended with zero target
  processes and zero QMP sockets.

## Inferences

- A positive swapchain readback with a black QMP screenshot would identify the
  loss after Vulkan, in the Wayland child/compositor/QMP path. A zero readback
  will move the investigation into Vulkan rasterization, attachment clear,
  shader output, or image-layout/content handling.
- Because the readback is asynchronous and can change timing, it is a
  diagnostic discriminator, not a product fix. Its QMP result must be
  interpreted together with the existing draw2 and present markers.

## Source/API relationship recorded by this ticket

`VulkanDriver::endRenderPass` owns the active `HwRenderTarget`, while
`VulkanReadPixels::run` owns the image-layout transition,
`vkCmdCopyImageToBuffer`, queue submission, fence wait, map, and callback
boundary. The diagnostic calls that existing API only when the target is the
native swapchain, its format is `VK_FORMAT_B8G8R8A8_UNORM` or `_SRGB`, and the
fixed QMP candidate region fits inside the 1280×800 extent. It does not change
camera, Scene, Renderable, render-pass, present, or Wayland behavior.
