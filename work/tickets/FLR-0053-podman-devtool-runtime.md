## Work unit

Provide a documented, reproducible Podman path for Mac-side Yocto Devtool work
that mounts the canonical `meta-fluorite-trial` source, keeps AGL read-only, and
reuses one persistent container plus one fixed host state directory. Build,
download, and sstate are subdirectories of that bind. Yocto TMPDIR is one
container-private tmpfs because the macOS shared bind cannot provide the
case-sensitive FIFO, Unix-socket, and xattr contract. The wrapper repairs stale
root ownership before running BitBake as the host UID; named volumes and
per-ticket state trees are not part of this contract.

## Facts

- Podman 6.1.1 is installed on the Mac host and no `podman-compose` provider is
  required by the direct wrapper.
- Two exploratory 6 GiB rootful machine attempts failed during root filesystem
  initialization (`fsck.ext2`/Ignition and `useradd: cannot lock /etc/group`).
  The exact failed machines were removed after inspection. A fresh 8 GiB
  rootful machine was then created once by the operator outside the project
  wrapper; the wrapper itself still never creates, starts, stops, or removes a
  machine.
- The existing Docker Compose contract already separates the project bind mount,
  read-only AGL source mount, and four persistent state volumes.
- Docker Desktop is no longer a provider for this workflow. Its obsolete Mac VM
  was removed only after exact inspection and explicit operator approval; the
  Podman machine, container, and fixed state bind were not removed.
- The Podman OCI image `localhost/fluorite-yocto-devtool:22.04` built
  successfully. The single container uses the canonical project bind, the
  read-only AGL bind, and one fixed state bind; no Podman named volume was
  created. Startup normalized stale `self-install/meta-flutter` entries and
  retained the fixed `external/meta-flutter` layer.

## Provider gate handoff

The one-machine/one-container Podman provider gate is passed. The
source-dependent source editing and generated-patch acceptance is intentionally
continued in FLR-0062, which owns the target/readback diagnostic. Mac-side
official `update-recipe` and recipe `do_patch` are now proven there; Mini PC

### Correction to Iterations 9–12

Later direct probes supersede the earlier filesystem hypothesis: the existing
state bind accepts non-root FIFO creation and nested
`cp -afl --preserve=xattr`. The observed FIFO failure was caused by stale
`root:root` directories under `TMPDIR/work`. The final wrapper repairs only
ownership in the fixed state bind and probes the exact operations before
Devtool; the container-local tmpfs experiment is not part of the contract.

The ownership repair only changes real directories and regular files. It does
not follow or modify stale/dangling symlinks, which are not writable state
objects and must not block startup.

The repair checks each candidate with `test -e` immediately before `chown`, so
an invalid directory entry that disappears during traversal is skipped rather
than treated as a reason to delete or rebuild the state.

## Iteration 9 — Yocto FIFO provider boundary (2026-09-10)

### Plan

Keep the existing canonical project bind, read-only AGL bind, fixed state bind,
machine, and one persistent container. Test whether the Devtool failure is a
source problem or a filesystem contract problem before changing any source.

### Facts

- `scripts/run-podman-devtool.sh modify filament-vk` passed the Yocto sanity
  check and parsed 3340 bb files, then failed at the first sstate task with
  `PermissionError: [Errno 13] Permission denied` from `os.mkfifo` below
  `/workspace/state/tmp`.
- Inside the same container, `/workspace/state` is `virtiofs`. Regular file
  writes work, but the BitBake UID `501:20` cannot create a FIFO there.
- The same UID can create and remove a FIFO at `/workspace/tmp`, which is
  container-local Linux `overlayfs`; its measured filesystem had about 5.1 GiB
  free at the probe. No source file or generated patch changed.

### Inferences

- The failed `modify` was caused by the macOS virtiofs/Yocto TMPDIR contract,
  not by `filament-vk`, the layer, or a duplicate container.
- Keeping durable source/build/download/sstate paths in the one existing host
  bind while placing only Yocto's FIFO-producing TMPDIR in the same
  container's Linux writable layer preserves the requested direct canonical
  mount and avoids a named volume or second state tree.

### Hypotheses

- H1: Reasserting `TMPDIR=/workspace/tmp` and probing FIFO support before every
  wrapper operation will let official Devtool `modify` continue in the same
  container.
- H2: The limited container writable layer may become a later storage gate;
  this must be observed before any image-sized operation and must not be
  hidden by creating another container or TMPDIR.

### UNKNOWN

- Whether recipe-scoped `modify` and `finish` complete after this provider
  correction. No patch generation is claimed yet.
- Whether the current container writable layer has enough headroom for the
  complete recipe operation; the measured 5.1 GiB is only a preflight value.

### Check / Act

- **Check:** virtiofs FIFO failure and Linux-overlay FIFO success are directly
  reproduced in one container. Provider correction is ready for static gates.
- **Act:** update the wrapper to use `/workspace/tmp`, reassert the existing
  build configuration, run static checks, then retry `modify filament-vk`
  through the same container. Record the first subsequent error without
  generating a hand-written patch.
