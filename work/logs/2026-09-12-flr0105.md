# FLR-0105 working log — LLVM symbol-entry caller ownership

## Plan

Use the FLR-0104 debug image and one-QEMU contract. Set a pending breakpoint at
the known `llvm::CmpInst::isOrdered` entry and collect only a bounded caller,
register, and instruction sample. Avoid broad guest-side symbol extraction
because the prior GDB run reached memory pressure and a diagnostic OOM.

## Facts

- FLR-0103 mapped the production OOPS RIP to
  `libLLVM.so.18.1` / `llvm::CmpInst::isOrdered` at file offset `0xb1d541`.
- The production QMP frame remains HUD-only while the self-made fixture
  produces native 3D pixels.
- The normal batch GDB client did not receive a signal-stop event for the
  kernel OOPS, so a symbol-entry breakpoint is the next smallest observation.

## Inferences

- The breakpoint result can distinguish a normal call from a corrupted
  indirect target or return state without changing renderer semantics.
- Debugger output must be bounded and the guest must not run additional heavy
  symbol tools while the production process is live.

## Hypotheses

1. A production-only shader/resource caller enters `isOrdered` normally.
2. The OOPS lands at `isOrdered+1` without a normal function entry.
3. Debugger overhead masks the fault and produces an inconclusive run.

## UNKNOWN

- The caller, producer, and source line of the invalid state.
- Whether the kernel-OOPS form produces a coredump usable by `coredumpctl`.

## Do

- Reused the FLR-0104 debug image and fixed Mini receiver in one QEMU.
- Started the production Demo under one `gdbserver` and a bounded GDB command
  file. The entry breakpoint hit once at the normal `isOrdered` entry,
  emitted registers and eight frames, disabled itself, detached, and exited.
- Captured the QMP frame and analyzed the native/HUD regions, then terminated
  QEMU through QMP. A receiver-path typo in the first serial-exec status
  attempt was retained as a harness failure and corrected without restarting
  QEMU.

## Check

- Normal LLVM entry: PASS. The captured caller chain reached
  `InstCombinerImpl::visitFCmpInst` and `InstCombinePass::run`, but the sample
  did not reach the outer Mesa/llvmpipe caller.
- Later OOPS: PASS as reproduced evidence at `isOrdered+1` in another
  `FEngine::loop` thread.
- QMP: PASS for capture and teardown; native `0/223200`, HUD `1250/100000`.
- Memory: warning only; no OOM occurred in this run before teardown.
- Product fix: not justified.

## Act

- Close FLR-0105 as a bounded debugger evidence unit. Continue in FLR-0106
  with a bounded 16-frame capture to expose the caller above LLVM before any
  source patch is considered.
