  contribution boundary.

## Static Dart/Native relationship

- Dart places lights in `scene.lights`; each entry carries `type`, `position`,
  `intensity`, `falloffRadius`, color, and cast flags.
- Native `SceneTextDeserializer` reads that list, constructs
  `Light(encodableMap)`, and `setUpLights()` passes it to
  `LightSystem::vBuildLightAndAddToScene()`.
- Native `Light::Deserialize` accepts `position` and `falloffRadius`, and
  `LightSystem::vBuildLight()` forwards both to Filament
  `LightManager::Builder`. The API path is implemented and exercised; the
  suspect is the value relationship.
- The shared Dart point light is `(0,5,1)` with `falloffRadius=300.1`, while
  Planetarium geometry is centered near `(-720,0,680)`. The distance is about
  990, beyond the declared falloff if both use the same world-space frame.

### Decision

- Test only the point-light position first. Keep camera, shape list, material,
  indirect light, scene, and QEMU capture profile unchanged.

## Inferences

- A point light at `(0,5,1)` cannot be assumed to illuminate geometry nearly
  1,000 world units away when its declared falloff is `300.1`.
- The black shape is not evidence of missing 3D or a QEMU capture failure;
  the next test should preserve the camera and measure color response.

## Hypotheses

- H1: direct point-light placement/falloff is the first cause.
- H2: Dart/Native light or lit-material wire format remains mismatched.
- H3: Native lit shader/shadow path remains black even with valid inputs.

## UNKNOWN

- Whether the first minimal correction is light placement, directional-light
  semantics, indirect-light deserialization, or a lit-material fallback.
