# FLR-0308 working log — FEngine loop page fault during production load

## Plan

- Reuse the fixed Mini image/receiver/build/TMPDIR and one QEMU.
- Reproduce the first runtime fault with bounded serial evidence.
- Compare load-volume and opt-in-probe conditions before patching engine or
  Fluorite material code.

## Do

Opened from FLR-0307 after the corrected serial-exec run reached production
startup but stopped before material setup. The first evidence is retained at
`$EVIDENCE_ROOT/flr0307-0001/emissive/` and includes the launch completion
record, bounded runtime slices, QMP frame/video, and exact teardown result.

The observed sequence is:

1. ViewTarget creation and the 60-item model load plan completed.
2. The FLR-0305 SUN was installed.
3. Vulkan swapchain, queue submit, and present markers were positive.
4. `FEngine::loop` PID 692 received a guest page fault and the engine loop
   stopped before production asset/material/draw markers.

No new source change has been made for FLR-0308.

The one-model light-enabled control used the same FLR-0307 image, fixed
receiver/build/TMPDIR, 4096 MiB QEMU, serial-exec launch, QMP capture/video,
and QMP teardown. It logged `limit=1 match=sequoia_ngp queued=1` and the
FLR-0305 SUN, but no production asset/material/draw marker. After about 35
seconds the guest again logged `FEngine::loop` with `#PF` and `Oops: 0000`.
The one-model QMP frame SHA-256 was
`f686a3c2769cb2bc59b362bdc1d956c2d1d128cbcbfa6ea45ffe2eb92b4a5265`.

A second one-model fault-map run captured the same boundary. The run-specific
RIP was inside the mapped executable range of `/usr/lib/libLLVM.so.18.1`.
The release image had no debug symbols, so `llvm-symbolizer`,
`llvm-addr2line`, `eu-addr2line`, and `addr2line` returned `??:0`. Historical
FLR-0030 maps the same relative boundary (`0xb1d541`) to
`llvm::CmpInst::isOrdered(llvm::CmpInst::Predicate)`, so the current result is
classified as a repeated LLVM/llvmpipe boundary, not as a new symbolized
source proof. GDB attach passed and showed the FEngine, JobSystem, llvmpipe,
Flutter, and Wayland threads. No coredumpctl record appeared.

The fault-map QMP frame and all eight video frames share SHA-256
`f686a3c2769cb2bc59b362bdc1d956c2d1d128cbcbfa6ea45ffe2eb92b4a5265`; native
ROI remained `0/144000`.

The light-disabled one-model control omitted only
`FLR0305_PRODUCTION_SCENE_LIGHT`. At 45 and 105 seconds it had no
`FLR0305_PRODUCTION_SCENE_LIGHT_SETUP_DONE`, no Vulkan present, no production
asset/material/draw marker, and no page-fault/OOM marker. Its QMP frame and
all eight video frames share SHA-256
`d4e96a65fd4f8e97bc1d762fc90cf2593bc2efb53a3125a72502fdae0f09395c` and its
native ROI was `0/144000`. This is a lifecycle control, not a successful 3D
case.

## Check

The one-model, light-enabled, override-disabled control is complete and
reproduces the fault. The light-disabled control avoids the fault but stalls
before present. The 60-item queue hypothesis is weakened; the FLR-0307 opt-in
patch causality hypothesis is not supported. Line-level LLVM symbol ownership
remains UNKNOWN without debug symbols.

## Act

Next: add an opt-in zero-intensity mode to the existing FLR-0305 SUN through
the Mac Devtool source and official patch flow. Do not interpret FLR-0307's
zero native pixels as a light/material result until this LLVM/llvmpipe
boundary is resolved.
