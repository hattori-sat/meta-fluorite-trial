- At approximately 347 seconds, guest `dmesg` reported a page fault/OOPS for

  `0x0000000091006750`.
- `/proc/644/maps` placed RIP in `/usr/lib/libLLVM.so.18.1`; using its

  maps to file offset `0xb1d541`.
- `llvm-symbolizer` resolved `0xb1d541` to
  `llvm::CmpInst::isOrdered(llvm::CmpInst::Predicate)` with source line
  `??:0`, matching FLR-0030. This is a mapped symbol boundary, not a causal

- The batch GDB client did not report a normal `Program received signal` stop

- A later guest `addr2line` invocation caused OOM at approximately 646 seconds

  diagnostic-resource failure. The final QMP teardown reported zero residual

### Inferences

- 2D HUD output remains healthy while the production native region is black;
  this is not a global Flutter, compositor, or QMP visibility failure.
- The first observed post-scene failure remains inside or below the queue
  present path, with a reproducible LLVM symbol boundary.
- The one-byte-into-function position makes bad control-flow/return state
  plausible, but no evidence yet identifies who created that state.
- The next GDB observation must set a minimal breakpoint at the LLVM symbol
  entry and capture only a bounded caller/register record. Broad guest-side
  symbol inspection is unsafe under the observed memory pressure.

### Hypotheses

1. A production command/resource path reaches a corrupt LLVM/llvmpipe state
   during post-scene work. Prediction: the symbol-entry breakpoint captures a
   production-only caller or argument pattern before the OOPS.
2. The symbol address is a corrupted indirect target or return address rather
   than a normal `isOrdered` call. Prediction: the symbol-entry breakpoint is
   not hit while the OOPS still lands one byte into the function.
3. The debug client and guest tooling alter timing or memory enough to mask
   the original signal. Prediction: a low-overhead breakpoint-only run
   reproduces the same boundary without OOM.
