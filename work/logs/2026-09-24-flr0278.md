# FLR-0278 working log — production grayscale render content

## Plan

- Use FLR-0277's same-image fixture and production QMP results as the baseline.
- Compare only the first production-vs-fixture content/target differences.
- Keep runtime logs bounded and require live-process plus chromatic QMP evidence.

## Facts

- Pure fixture late ROI: 3,562 chromatic pixels, max chroma 242.
- Production late ROI: zero chromatic pixels in both normal and frame-event-skip
  cases. The initial liveness checks passed, but the normal production and
  model-only processes later produced delayed `SIGSEGV` coredumps.
- Model limit is one and QEMU memory is 4096 MiB.

## Do / Check — 2026-09-24 production A/B

- The single QEMU run directory was `flr0278-0001`; the harness was started
  with `--memory-mb 4096` and the QMP-only capture path was used.
- The guest reported 3,991 MiB total, 3,150 MiB free, and 3,560 MiB
  available. The bounded kernel search found no OOM-killer, cgroup-memory, or
  killed-process record. This falsifies QEMU memory exhaustion as the cause of
  this run.
- The lights-on production case initially produced 72 chromatic pixels, but
  the late frame returned to zero chromatic pixels (`lights-video/frame-00009.ppm`,
  SHA-256 `f686a3c2769cb2bc59b362bdc1d956c2d1d128cbcbfa6ea45ffe2eb92b4a5265`).
  Its process later produced a `SIGSEGV` coredump (PID 643).
- The model-only case skipped shapes but retained production lights. It emitted
  model-load and draw/present markers, while initial and all late QMP frames
  were uniform `224,224,224` in the ROI: zero chromatic pixels and zero edge
  pixels (`model-only-video/frame-00009.ppm`, SHA-256
  `a4ffc7bb0f07ccbc213989a8874f2a80755d84d808f3b85e39fdc10c68056bbb`).
- The model-only process later produced a `SIGSEGV` coredump (PID 733). The
  bounded `eu-stack` result is:
  `FilamentViewPlugin::CallEvent -> ViewTarget::DrawFrame -> ViewTarget::OnFrame`
  on the ECS thread; the Vulkan/llvmpipe threads were waiting in queue submit or
  present. This is an application callback fault, not an OOM signature.
- The stop command passed through the serial harness, QMP quit was accepted,
  residual targets were zero, and the QMP socket was absent after teardown.
- Visual inspection of the retained QMP frames confirms the metrics: the
  lights-on initial frame shows the 2D HUD and button over a black 3D area;
  the model-only late frame shows a large uniform white/gray upper surface
  over a black lower band, with no vehicle, outline, or other production model
  content visible. The screenshots do not support calling this successful 3D.

## Inference

- The 4 GiB guest allocation is sufficient for this bounded one-model run;
  increasing it is not an evidence-based fix for the current failure.
- Skipping shapes does not explain the grayscale output: production remains
  uniform gray without shape setup.
- Enabling production lights does not restore sustained chromatic pixels and
  is unsafe in the current unskipped frame-event path because the delayed
  `CallEvent` fault still occurs. The light/content hypothesis remains open,
  but it is not yet a successful visual discriminator.

## UNKNOWN

- Whether the uniform gray ROI is a production PBR/material result or a parent
  surface/composition result is still unknown; the visible full-width white
  surface makes the latter a stronger next discriminator.
- The exact `CallEvent` invalid state is not yet identified; FLR-0277's skip
  control remains the safe isolation control for the next content experiment.

## Act

- Keep QEMU at 4096 MiB and keep the same run/evidence layout.
- Do not spend another iteration increasing memory. First inspect the
  production material-instance and target-content contract against the proven
  unlit fixture, using the frame-event skip control to avoid conflating the
  callback fault with render content.
