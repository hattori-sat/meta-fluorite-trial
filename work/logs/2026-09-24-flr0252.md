## Check

### Facts

- The production route reaches asset-ready, model selection, Scene insertion,
  draw submission, and queue present before failing runtime health.
- The app is killed by the guest OOM killer before a stable production 3D
  frame or route-transition input can be proven.
- The white settled frame is post-failure evidence, not proof of a valid
  production scene render.
- The self-made fixture is not active in this run; its ROI is therefore not a
  control success and remains black as expected.

### Inferences

- The immediate next boundary is production asset/Scene lifecycle memory
  growth, before a meaningful Wayland composition or QMP input conclusion.
- The high model-selection and Scene-add counts relative to only ten asset
  loads suggest repeated selection/addition or retained scene resources, but
  this is a hypothesis until the source loop and allocation ownership are
  inspected.
- The evidence does not yet establish whether the production models are
  individually too large, repeatedly instantiated, or retained by an
  unbounded callback/frame loop.

### Hypotheses

1. Production model selection/Scene insertion is repeated without a one-shot
   or cleanup guard, retaining Filament entities/resources until OOM.
2. One or more production GLB assets exceed the guest memory budget even with
   one intended load.
3. The route repeatedly rebuilds the scene while `beginFrame=false`, causing
   both scheduling and memory growth; the white frame is a consequence of the
   OOM rather than a standalone composition defect.

### UNKNOWN

- Which allocation or object owner grows between the first and last asset
  load.
- Whether a single production model can render a stable 3D pixel frame within
  the current guest memory budget.
- Whether Scenes input reaches the intended route after the memory issue is
  removed.

## Act

- Close FLR-0252 as a baseline classification and open FLR-0272 for the
  production asset/Scene OOM boundary.
- Inspect the current source loop and ownership before any code change.
- Keep the next runtime run bounded and use the same image/profile after a
  minimal, evidence-backed change.
