  nonzero-offset readback buffers cause the delayed full-frame blackout.

  commit the source, finish the official patch, register it in
  `meta-fluorite-trial`, and build on the Mini PC.
- Run one QEMU instance with the fixed harness, capture ten QMP-only frames,
  and prove teardown.

  `f686a3c2769cb2bc59b362bdc1d956c2d1d128cbcbfa6ea45ffe2eb92b4a5265` and

- The remaining failure is narrower than the previous whole-frame blackout.
  Runtime source pixels and Wayland requests are valid, but the readback child

## Hypotheses

- H1 shared-pool lifetime/import interaction: may affect the early timing
  window, but separate storage did not durably remove the whole-frame blackout
  and is not sufficient to make 3D visible.
- H2 callback or buffer release ownership: not the leading boundary for this
  run because both readback buffers were attached, committed, and released.
- H3 readback child visibility/import/QMP composition: remains open and is
  transferred to FLR-0271.

## Check

- Full-frame QMP: PASS only for the early ten-frame window in `0289`; the
  follow-up `0290` window is FAIL with five consecutive full-black frames.
- Readback ROI `(460,260,360,280)`: FAIL, `0/100800` changed and
  `0/100800` chromatic in all ten frames.
- Runtime readback counters: PASS, both slots reported
  `100800/100800` nonzero and chromatic pixels.
- Protocol errors: none observed in the bounded serial slice. Surface creation,
  parent/position/stacking, and readback publish were all recorded before the
  later black QMP frames.
- Teardown: PASS, QMP quit accepted, `residual_targets=0`,
  `residual_qmp=0`.

## Act

Close FLR-0270 as a partial diagnostic result and make FLR-0271 the sole
`In Progress` unit. Do not treat the diagnostic SHM path as production Fluorite
3D success. The next run must capture the first creation/parent/position/
stacking events of the readback surface and compare them with the known-good
SHM-only control.

## Metadata and lock decision

- Patch `0271` was inspected. Its author trailer is already the anonymous
  `Fluorite Devtool <fluorite-devtool@example.invalid>` identity; no personal
  email remains in that patch. Repository privacy check returned PASS, so no
  content change is justified.
- A Git `.git/index.lock` is a transient mutex created by Git during an index
  write; it must not be committed or kept as project state. The Podman/Devtool
  operation lock is a separate short-lived guard that serializes operations on
  the single shared source/build state and is released on exit.
- `manifests/baseline-sources.lock` and `pubspec.lock` are reproducibility
  records, not parallel-operation mutexes. They should remain when their
  tracked inputs/dependency graph require them; no new index lock is needed
  for this single-agent run.
