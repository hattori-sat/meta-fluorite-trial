## Inferences

- This is not a transient single-screenshot artifact.
- The white transition is not caused specifically by button-up delivery,
  because it appears at `move-y` before `down` and `up`.
- The native 3D path is not the first failing boundary in this run: the native
  ROI is unchanged while only the HUD changes.

## Hypotheses

1. A pointer-motion/region-entry path changes the parent to a uniform white
   buffer independently of button-up delivery.
2. A delayed parent-surface damage/import or Flutter frame path changes the
   parent after an input-related update.
3. A Wayland protocol or compositor ordering event changes which parent buffer
   is visible while native content remains valid.

## Plan / Do / Check / Act

### Plan

Keep the same image and metrics-skip environment. Compare a no-input time-only
control against the input sequence, then isolate `move-x` and `move-y` with
repeated post-event frames. Inspect only selected parent-surface Wayland
attach/damage/frame markers and Flutter frame markers around the first white
frame.

### Do

Added the deterministic repeated-input QMP script and fixed launch/stop
commands in commit `8867019`. The commit was bundled to the Mini receiver and
the runtime run completed with one QEMU process.

### Check

The first white transition in the repeated input run is `move-y`; it persists
for all remaining frames. The valid no-input control remains chromatic for all
25 frames, so pure time and QMP screendump repetition are falsified. The
single-axis controls remain chromatic; the combined run is the first one with
the logged `wl_pointer.motion` event, so the exact source owner is now narrowed
to pointer-motion delivery versus the parent-surface path.

The first no-input attempt at
`$EVIDENCE_ROOT/FLR-0232/qemu-no-input-ready/` is recorded as a process FAIL,
not runtime evidence: frame 23 was not yet visible when the script checked,
and the outer runner lacked `set -e`. Commit `dc4618f` added a bounded file
wait, and the rerun used `set -eu`.

### Act

The move-x-only, move-y-only, and no-input controls are complete. Close
FLR-0232 and move the sole In Progress focus to FLR-0233 for the official
pointer-motion gate.
