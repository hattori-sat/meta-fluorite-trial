# FLR-0277 working log — production `CallEvent` SIGSEGV boundary

## Plan

- Preserve the FLR-0276 evidence and use it as the starting baseline.
- Compare the two leading explanations: invalid/concurrent frame-event state
  versus production workload-triggered asynchronous render race.
- Inspect source and collect one bounded runtime/core discriminator before
  editing or generating any new patch.

## Facts

- FLR-0276 proves one-model selection at 4096 MiB and a positive colored pure
  fixture in the same QEMU.
- The production core's first application frame is in
  `plugin_filament_view::FilamentViewPlugin::CallEvent(...)`, called by
  `ViewTarget::DrawFrame(unsigned int)`.

## Hypotheses

| Hypothesis | Prediction | Status |
| --- | --- | --- |
| invalid/concurrent `eventBus` or callback state | a bounded event-bus/frame-event discriminator changes or removes the crash | Open |
| production workload exposes an async render race | narrowing the production workload changes the crash while event-bus state remains valid | Open |

## Do / Check

### Static analysis

- `ViewTarget::DrawFrame()` calls `FilamentViewPlugin::CallEvent()` after the
  native render/present path and waits on the returned future.
- `CallEvent()` inserts into the static `_eventCallbacks` map and calls the
  static `eventBus` channel. The map has no mutex, and the event-bus pointer
  has no explicit lifetime guard. These are competing crash explanations,
  not yet a proven root cause.
- The callback handler also erases the same map from the Flutter method-call
  path. The pure fixture reaches the same frame path without crashing, so the
  production workload may be exposing a race rather than making the call
  unconditionally invalid.
- Historical patch `0061` used a frame-event skip discriminator, but it is not
  active in the current recipe. Its old hunk does not apply to the current
  source, so it was not copied as a layer patch.

## Decision

- The unconditional `CallEvent`/event-bus hypothesis is not proven as the
  cause of the current production 3D failure: normal production survived,
  skip production also survived, and skipping the event did not restore color.
- A race remains possible because the static map/channel ownership is still
  unprotected, but it needs a separate stress/core reproduction before a
  safety fix is justified.
- The first selected boundary is now production scene content/material/
  lighting or target state: the same image and QEMU render colored fixture
  pixels but production produces black/grayscale pixels.
- FLR-0278 owns that next boundary; route/input validation remains blocked by
  the absent production chromatic-pixel gate.

## Act

Close FLR-0277 as a completed diagnostic A/B and move the sole In Progress
focus to FLR-0278. Keep the frame-event gate available for later stress
reproduction, but do not treat it as a production 3D fix.
