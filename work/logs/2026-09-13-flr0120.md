- Static comparison after the build found that Dart's generated API declares
  `setCameraOrbit`, `setCameraTarget`, `setActiveCamera`, and
  `setCameraDolly`, while native `messages.g.h/.cc` has no corresponding
  handlers. Native exposes only the older `changeCamera...` and
  `setCameraRotation` camera channels.
- Static comparison also found that Dart sends cameras at root-level
  `creationParams["cameras"]`, while native root deserialization handles only
  `models`, `scene`, and `shapes`; the native camera is created from
  `scene.camera`.

### Inferences

- The 0232 registration-order change is not the direct fix. It moved setup
  earlier, but it cannot register methods absent from the native generated
  API. The identical post-0232 errors falsify the order-only hypothesis.
- The current camera bridge is an API-generation mismatch compounded by a
  payload-placement mismatch. This is now the leading cause of the fixture's
  camera state not reaching the native ViewTarget.
- The next smallest experiment is to restore `scene.camera`, omit the ignored
  root `cameras` payload, and stop Dart-side initialization calls. If that
  removes the channel errors and changes QMP pixels, the native v2 camera
  contract is confirmed. If not, the remaining black result is a separate
  render/surface boundary.

### Hypotheses / UNKNOWN

1. **Selected:** restore the v2 scene-camera payload and remove unsupported
   Dart camera method calls; prediction is no camera `channel-error` and a
   native camera-application marker.
2. **Alternative:** regenerate/extend native Pigeon API and implement the new
   camera operations; this is broader and riskier because the native core has
   no matching `setCameraDolly`/`setCameraOrbit`/`setCameraTarget` methods.
3. **UNKNOWN:** whether correcting the camera contract alone will make the
   self-made cube visible; historical fixture-positive runs prove the native
