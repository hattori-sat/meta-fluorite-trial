## Inference

The bounded loader fix separates the former guest-OOM loop from the first
remaining render-content boundary. The 0087 root-camera correction did not
reach the native camera receiver; the proven `scene.camera` contract is now
the next controlled variable.

## Hypotheses

1. **Falsified:** the current Dart `scene["camera"]` payload is ignored and
   root `cameras` is the supported path. Run 0300 with 0087 produced zero
   camera-receive/application markers.
2. **Selected:** restoring the historically proven `scene.camera` payload and
   omitting root `cameras` will restore the native camera handoff. This is
   pending Mini build/runtime verification.
3. Even with a corrected camera, projection/lighting or Wayland child-surface
   composition may still suppress chromatic pixels. This remains untested.

## Failed/retained observations

- The model limit keeps the guest alive, but a grayscale frame is not accepted
  as 3D success.
- A count label printed by an earlier log-slice command was not treated as a
  raw runtime camera marker; raw lines are the authority.

## Run 0302 and native-parser correction

Run 0302 used the 0089 image. The Dart trace proved
`FLR0272_CAMERA_PAYLOAD cameras=7 scene=true scene_camera=true`, but the raw
runtime still had zero native camera receive/application markers. QMP start,
guest readiness, Flutter launch, bounded log capture, still/video capture,
negotiated quit, and residual cleanup passed. The initial and late PPM SHA-256
was `f686a3c2769cb2bc59b362bdc1d956c2d1d128cbcbfa6ea45ffe2eb92b4a5265`; the
production ROI remained `22.893%` changed, `chromatic_pixels=0`,
`max_chroma=4`.

Static inspection of the exact Mini native source corrected the previous
history-based inference:

- `DeserializeRootLevel()` handles root `cameras` and constructs native
  camera entities; `DeserializeSceneLevel()` has no `camera` branch.
- Native `Camera` decodes Dart `viewId=-1` as the null view id and the update
  loop skips it.
- The generated `setActiveCamera` channel is implemented and calls
  `ViewTargetSystem::setViewCamera()`.
- The production image always mounts `PlanetariumSceneView`, but FLR-0241 had
  made its `onCreate()` inert, so no camera was selected for view 0.

The selected correction is therefore root `cameras` plus camera initialization
and Planetarium `setActive()`. The two-file source change was made in the
persistent Mac Devtool source and committed as
`4944f3f5d20ef65cc10883d144f07ea40585e77f`. Official Devtool finish generated
one patch, copied unchanged as
`0090-flr0272-restore-root-camera-activation-contract-devtool.patch`, with
SHA-256 `450580a6b0517d6dd08bb28b91c6a9923edc620784a2e1f25f1aa7f290ee3202`.

The first finish attempt generated zero patches because `modify --no-extract`
