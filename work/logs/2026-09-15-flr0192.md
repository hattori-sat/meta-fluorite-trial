# FLR-0192 working log — defer ViewTarget creation until ECS init

## 2026-09-15 opened from FLR-0191

### Facts

- FLR-0191 QMP proved 2D pixels and Vulkan submit/end-frame while the fixed 3D
  region remained uniform black.
- Runtime emitted `CREATE_ENQUEUED` and `START_ENQUEUED`; the start handler
  reported `count=0`; the create handler did not appear.
- `RunOnceCheckAndInitializeECSystems()` posts system construction and
  `ecs->initialize()` to the ECS strand without waiting in the Mini effective
  source. `ECSManager::RouteMessage()` synchronously iterates the current
  `_systems` map and calls `SendMessage()`.
- `DeserializeDataAndSetupMessageChannels()` waits until system pointers exist,
  which explains why the later start route is delivered while the earlier
  create route is absent.
- Current API names are `initialize`, `RouteMessage`, `getStrand`, and
  `StartMainLoop`. The stale 0236 APIs `vInitSystems` and `vRouteMessage` are
  absent and are out of scope.

### Inference

- Leading cause: the create request is routed before ViewTargetSystem exists,
  so it is lost rather than queued for later handler registration.
- Secondary cause to falsify: cross-thread queue ownership or handler timing.

### Hypotheses and decision

- Compare synchronous ECS initialization wait against a same-strand deferred
  create route. The deferred route is preferred because it preserves the
  non-blocking design and avoids an unconditional wait if registration ever
  occurs on the ECS API thread.

### Check

- No source change started yet.
- No new build or QEMU process is running.

### Act

- Implement only the chosen current-API ordering fix in the persistent Mac
  Devtool source, then use official Devtool generation and the progressive
  Mini gates.
