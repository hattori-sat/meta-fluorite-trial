# FLR-0079 — current-image forced-fixture present boundary

## Facts

- The fixed Mini image rootfs is SHA-256
  `92c656e4cfca05f69f25429569bcc2700192240d163cb8bee0d5b60db77a5445`.
- p10 and p11 used the fixed runqemu profile and separate evidence directories
  under `$QEMU_EVIDENCE_ROOT/flr0078`; no second QEMU was active.
- p10 passed preflight, start, guest-ready, and serial-login. Its app PID was
  not proven because the follow-up serial probe was initially run against the
  Mac localhost instead of the Mini localhost. The QMP control and five-frame
  hashes were all
  `d4e96a65fd4f8e97bc1d762fc90cf2593bc2efb53a3125a72502fdae0f09395c`, with
  candidate `0/223200` and HUD `0/100000`.
- p11 used a Mini-side persistent serial connection. The guest query showed
  two `flutter-auto` processes owned by `agl-driver`.

## Inferences

- p11 is a valid runtime control attempt: the process and setup markers prove
  the fixture was not merely a boot/control frame.
- The first currently observed divergence is after queue-present markers and
  before `PRESENT_BOUNDARY_DONE`; the black QMP frame is not enough to call
  this a Flutter launch failure.

## Hypotheses

1. Frame/fence skip handling prevents the present-boundary callback despite
   forced-frame markers.
2. The Wayland surface is created but not committed/visible to the QEMU
   compositor.
3. The current 0208 artifact/profile differs from the historical visible
   fixture at an unrecorded provenance boundary.

## Decision

Move FLR-0079 to Waiting. p13 falsifies duplicate app launch under the fixed
profile and classifies the current control's first observed divergence at the
repeated unlinked fence/status path before the visible present boundary. The
same pattern is present in earlier black production runs, so this is a runtime
classification rather than a product root-cause claim. Continue in
[FLR-0080](../tickets/FLR-0080-current-image-frame-recovery.md), which tests
the existing ready-fence diagnostic as one variable before any source patch.
