recipe-applied baseline and already supported bounded model loading; no new
source patch or image build was made for this diagnostic.

The authoritative Mini run used the fixed receiver/build/TMPDIR and one
QEMU. The production launch used the current controls:

- `FLR0026_NATIVE_MODEL_LIMIT=1`
- `FLR0026_NATIVE_SKIP_SKYBOX=1`
- `FLR0026_NATIVE_SKIP_INDIRECT_LIGHT=1`

`plugin_filament_view::FilamentViewPlugin::CallEvent(...)`, followed by
`ViewTarget::DrawFrame(unsigned int)`. Another thread was in llvmpipe/LLVM
code generation and another was in the Wayland present callback.

The fixture was launched without starting another QEMU. Its QMP evidence was
captured before teardown.

## Inferences

- Increasing QEMU memory from the fixed 2048 MiB profile to 4096 MiB removed
  the previous OOM ambiguity and allowed a one-model production experiment.
- The fixture's colored QMP pixels in the same QEMU falsify a generic QEMU,
  Wayland, or QMP capture failure.
- The first current production fault boundary is the frame-event path around
  `CallEvent`, but the exact invalid object or race is UNKNOWN. The concurrent
  llvmpipe/LLVM activity is evidence of workload overlap, not proof of the
  root cause.

- Whether the production model/material path only exposes the race through
  llvmpipe/LLVM work is not yet proven.
