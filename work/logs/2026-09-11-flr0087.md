# FLR-0087 — serial-exec completion evidence

## Plan

Fix the evidence harness only after reproducing its malformed completion
record, then validate it on the already-running QEMU.

## Facts

- `serial-exec` synchronized to the guest shell prompt and executed the
  harmless `true` command, but its parser reported
  `completion-status-not-observed`.
- The saved serial output ended exactly at
  `__FLR_SERIAL_COMMAND_DONE_7B31__`; the receiver stopped reading before the
  following `rc=...` field.
- A runtime discovery command also executed and produced guest identity,
  executable, and release-file output, but was rejected for the same parser
  defect.

## Inferences

- The marker was placed before the status, so marker detection truncated the
  stream before status parsing. This is a deterministic harness bug.

## Hypotheses

1. Emitting `rc=<number>` before the marker allows the existing bounded socket
   loop to capture a complete status record.
2. The active QEMU and guest remain valid because the commands themselves ran.

## UNKNOWN

- The reason `flutter-auto` exited during the first launch attempt is not yet
  determined; that remains FLR-0086 runtime evidence.
