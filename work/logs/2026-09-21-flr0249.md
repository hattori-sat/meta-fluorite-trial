Date: 2026-09-21

## Plan

Start from the FLR-0248 exact source/layer/image baseline. Inspect the native
plugin's readiness channel registration order, messenger, and lifetime. Make
one minimal correction, then use the official Mac Devtool patch flow and the
authoritative Mini build/runtime gates.

## Facts

- FLR-0248 proved stable 2D HUD and self-made native 3D pixels.
- FLR-0248 proved zero native readiness handler receives in the runtime.
- The FLR-0248 `flutter-auto` binary and rootfs artifact contain the
  `FLR0248_NATIVE_CALL_RECEIVED` and `FLR0248_NATIVE_CALL_RESPONDED` strings,
  so the diagnostic native source reached the built artifact.
- The FLR-0248 serial order was: Dart calls at `19:57:54.567824` and
  `19:57:54.615747`, C API registration at `19:57:54.640469`, and C API return
  at `19:57:55.281792`. The first two calls preceded registration.
- The native readiness channel is currently created in
  `setupMessageChannels()` after the PlatformView registration path starts.
  The Flutter header used by this build says `MethodChannel` does not
  unregister its handler on destruction.

## Inferences

- The next useful boundary is native channel registration/reachability, not
  scene rendering or composition.
- The first two `MissingPluginException` results are explained by the Dart
  poll starting from `initState` before PlatformView creation. A candidate
  correction is to start the poll from the existing `SceneView.onCreated`
  callback, after native registration returns.
- Because later calls still did not reach native in FLR-0248, the ordering
  correction must be validated once before any native channel lifetime change
  is considered.

## Hypotheses

1. Registration timing is too late or tied to a different messenger.
2. A local channel owner does not remain stable through engine activation.
3. The channel identity differs only in the effective runtime.
