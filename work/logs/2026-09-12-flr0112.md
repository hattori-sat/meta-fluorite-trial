## Iteration 3 — audit the effective Devtool patch stack before the next runtime A/B (2026-09-12)

### Plan

- Inspect the canonical `flutter-auto_2.0.bbappend` order and the persistent
  Mac Devtool source tree before proposing another rendering patch.
- Separate unconditional runtime behavior from environment-gated diagnostics.
- Compare at least two explanations for the production-only failure and keep
  the next runtime test bounded to one same-image triad.

### Facts

- The canonical recipe currently lists 130 patch entries for `flutter-auto`.
- The effective base behavior includes Vulkan backend selection,
  `wl_subsurface_place_above`, transparent Filament clear and swapchain,
  software-frame scheduling, asynchronous platform registration with a
  serialized ECS initialization point, initial view-message draining, and
  platform-runner dispatch for frame events.
- The effective source also contains unconditional model/asset lifetime
  changes: snapshotting indirect-light inputs for asynchronous work, preserving
  the ECS owner, restoring queued non-instanced asset pointers, and deferring
  source-data release until scene insertion. The camera point-target condition
  is also an unconditional behavior correction.
- The later patch order gates the extra surface commit/damage/flush,
  readback, force-opaque, scene-isolation, light-isolation, camera trace, and
  fixture controls behind `FLR0026_*` or `FLUORITE_*` environment variables.
- In the effective source, normal production execution keeps the explicit
  pre-present/synchronous commit probes disabled when those variables are
  absent; `wl_subsurface_place_above` and transparent swapchain remain the
  normal base behavior.
- Historical QMP evidence under this project history contains both a
  self-made native fixture plus Flutter HUD and a model-only black vehicle
  plus red lamps. Full production remains HUD-only or uniform in the native
  candidate region.

### Inferences

- The current patch stack is a significant confounder, but it is not evidence
  that every native draw is broken: fixture and model-only positive controls
  have crossed the same broad native/compositor path in historical runs.
- The full-production failure is more consistent with a production-scene
  resource/render/present boundary than with a universal Flutter 2D or QMP
  failure. This remains an inference because the positive controls are not yet
  a same-image, same-run triad.
- Adding another unconditional surface or lighting patch before that triad
  would make the causal boundary less observable.

### Hypotheses

1. Base composition/frame-loop behavior is a regression. Reverting only the
   behavior-changing subset while keeping the same production scene should
   change the QMP native-region result without changing scene markers.
2. Production model/resource/lighting work diverges after scene setup. A
   same-image triad should show pure fixture and model-only geometry indicators
   while full production remains native-black or HUD-only.
3. Native pixels exist before final composition but are hidden. A delayed
   native readback and final QMP capture from the same run should disagree.

### UNKNOWN

- Whether the production native surface contains geometry before Wayland/
  Flutter composition.
- Whether a minimal behavior-baseline build can be produced on the Mini

### Camera separation

- Camera setup requires an ECS entity with both `Camera` and `Transform`; the
  deserializer registers the entity and initializes the ViewTarget after scene
  setup. The runtime then applies the camera model matrix and projection.
- In the current production-positive model-only controls, the camera was
  `(5,0,-5)` with target `(0,0,0)`, near `0.05`, and far `1000`; the same
  camera-applied and valid-view evidence is present in the full-production
  zero-pixel controls. Therefore camera application is **not** the current
  first stable cause of the black production target.
- A real historical camera-side failure did exist in the first fixture route:
  it called the production camera graph and hit a null camera-list exception
  before native scene creation. The camera-isolated fixture removed that
  dependency; later pure-fixture runs reached native pixels. This must not be
  conflated with the current production light boundary.
- UNKNOWN: whether a particular production camera target or projection can
  still hide a subset of geometry. Existing successful model-only output with
  the applied camera makes it a lower-ranked hypothesis, not a falsified
  possibility for every route.

### Light separation

- With `DEFAULT` indirect light and skybox skip/clear held constant, enabling
  the explicit production lights produced zero candidate pixels, while
  skipping them produced `4905/223200`. Both cases reached model completion,
  camera application, submit/present, and QMP teardown.
- Selecting one explicit POINT light did not recover output: GUID 126 alone
  and GUID 128 alone both remained `0/223200`. The first-light identity
  hypothesis is therefore rejected.
- The runtime light trace proved that at least one selected light had a valid
  Filament entity, valid light component/instance, Scene membership, and a
  nonzero Scene light count. A trace-enabled positive frame occurred once but
  was not reproduced in the fixed follow-up; it is a timing observation, not
  a fix.
- Current inference: the failing step is after or around explicit-light
  participation in the shaded material/resource/output path. The exact
  operation remains UNKNOWN; `BuildLight` and `Scene::addEntity` must not yet
  be called the confirmed root cause.

### Decision

- Do not spend another runtime cycle on generic 2D, QMP, camera, or light-count
  repetition. The next bounded test must compare the explicit-light operation
