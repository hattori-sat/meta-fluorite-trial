# FLR-0121: align the Dart camera payload with the native v2 contract

## Outcome

Prove whether the self-created Flutter Filament fixture can produce visible
native 3D pixels when its camera is serialized through the native scene
contract. This ticket is a camera/composition boundary experiment; it is not
yet a production vehicle or Sequoia validation.

## Success criteria

1. The fixture does not call generated Dart camera methods that have no native
   handler.
2. The native deserializer receives the camera in the `scene.camera` field it
   actually consumes; unsupported root `cameras` data is omitted.
3. Mac `do_patch` passes using a patch generated by the official Yocto
   Devtool workflow, and the byte-identical patch is registered in
   `meta-fluorite-trial`.
4. The Mini authoritative receiver accepts the bundle and the existing
   qemux86-64 build completes without deleting protected caches.
5. QMP-only early and late screenshots are captured from one official QEMU
   instance. The central 3D region has a non-black, chromatic or edge signal,
   or the evidence clearly falsifies this camera hypothesis and opens the
   next ticket.

## Facts

- The current fixture reaches Vulkan submit and the 2D HUD is visible, but the
  central 3D QMP region is uniformly black.
- The Dart generated API declares `setCameraOrbit`, `setCameraTarget`,
  `setActiveCamera`, and `setCameraDolly`.
- The native generated API exposes only the legacy camera methods and has no
  handlers for those four Dart method names.
- The native root scene deserializer consumes `models`, `scene`, and `shapes`;
  it does not consume a root `cameras` list. It consumes a camera under
  `scene.camera`.
- Historical project patches already describe the intended adapter shape:
  inject the first fixture camera into `scene.camera`, omit root `cameras`,
  and avoid Dart ECS camera initialization for the native ViewTarget camera.

## Inferences

- The observed `channel-error` messages are a direct Dart/native generated API
  mismatch, not evidence that the native renderer failed to submit.
- The previous camera-registration-order fix was insufficient because it
  changed channel readiness, not the incompatible payload and method names.

## Hypotheses and alternatives

### Selected: adapt the Dart fixture to the existing native v2 boundary

Serialize the first camera into `scene.camera`, remove root `cameras`, and do
not initialize the Dart camera as an ECS object after platform-view creation.
This is the smallest change and uses the native contract already present in
the image.

### Deferred alternative: extend and regenerate the native Pigeon API

Add native implementations for all four new camera methods and regenerate both
sides of the API. This would preserve the current Dart object lifecycle but
expands native behavior, Pigeon compatibility, and regression surface. It is
only justified if the selected adapter removes the channel errors but cannot
produce 3D pixels.

## Execution and evidence

1. Run the canonical-repository guard and keep FLR-0121 as the only active
   ticket.
2. Start the existing rootful `fluorite-devtool` Podman machine and reuse the
   single `fluorite-mac-devtool` container and fixed bind-mounted state. Do not
   create a per-ticket volume, temporary build directory, or second container.
3. Edit the registered Devtool source tree, run source diff checks, and commit
   only the source change with the Devtool source Git identity.
4. Run official `devtool update-recipe`/patch generation for the component.
   Inspect the generated patch and copy it unchanged into the layer; never
   hand-author the patch body.
5. Register the patch after the existing fixture patches, update the approved
   baseline lock if required, and run the Mac `do_patch` gate.
6. Commit the layer patch, recipe registration, lock, ticket, and working log.
7. Bundle the canonical commit to the fixed Mini authoritative receiver and
   run the progressive BitBake build there.
8. Launch one official `runqemu` instance, use QMP for screenshots and quit,
   analyze only the fixed evidence regions, and record success or failure.
9. If the central region remains black, leave FLR-0121 Waiting with evidence
   and create a separate ticket for the next boundary (geometry/material or
   surface composition); do not mix that diagnosis into this change.

## Risk and rollback

The adapter changes only the fixture's camera serialization and lifecycle. It
does not change production scene assets or the native renderer. If Mac
`do_patch`, Mini build, or QMP validation fails, preserve the generated logs,
do not delete caches, and revert only by selecting the prior committed layer
revision in a new ticket; do not reset the working branch.
