# FLR-0410 — Event Callback Map Race Implementation Plan

> **For agentic workers:** Use the `executing-plans` skill to implement this plan task-by-task, preserving its checkpoints.

**Goal:** Serialize every access to Filament's Flutter event-callback map and erase each completed event before waking the ECS frame waiter, then validate on a newly built candidate image.

**Architecture:** Keep one file-local mutex around the static callback map. A single completion helper takes the promise and erases the entry under the mutex, unlocks, and only then fulfils the promise. The renderer and event protocol stay active; no input, repaint, scene, or present behavior is bypassed.

**Tech Stack:** Yocto Project Devtool in the existing Podman container; C++17 `std::mutex`/`std::map`/`std::promise`; `meta-fluorite-trial`; Git bundle; Mini PC BitBake; QEMU/QMP.

## Task 3: Make the minimal Devtool source change

**Files:**
- Modify only: Devtool-managed `plugins/filament_view/filament_view_plugin.cc`

**Synchronization contract:**

```cpp
namespace {
std::mutex eventCallbacksMutex;

bool completeEventCallback(const int64_t eventId) {
  std::shared_ptr<std::promise<void>> promise;
  {
    std::lock_guard<std::mutex> lock(eventCallbacksMutex);
    auto it = FilamentViewPlugin::_eventCallbacks.find(eventId);
    if (it == FilamentViewPlugin::_eventCallbacks.end()) {
      return false;
    }
    promise = std::move(it->second);
    FilamentViewPlugin::_eventCallbacks.erase(it);
  }
  promise->set_value();
  return true;
}
}  // namespace
```

Protect insertion with the same `eventCallbacksMutex`:

```cpp
{
  std::lock_guard<std::mutex> lock(eventCallbacksMutex);
  FilamentViewPlugin::_eventCallbacks[eventId] = std::move(promise);
}
```

- [x] `<mutex>` was not directly included; the source now includes it explicitly.
- [x] Implemented one take/erase-under-lock helper and routed success, error, not-implemented, and `ret_*` completion through it. The `ret_*` result is success only when the helper finds the event.
- [x] The mutex is not held during `InvokeMethod`, `promise->set_value()`, or `future.wait()`.
- [x] Enumerated all map references across the component: only the locked insertion and locked helper read/erase the map; remaining references are declaration/definition. `_eventIdCounter` has one `CallEvent` writer/call path and is unchanged.
- [x] Wrapper diff/status checks found exactly one source path. Devtool source commit `0290b78ad139c9572b15b9e02f077421f3903b09` has parent `c9ffc87dee884af62099a18f95d7c72642997708` and changes only `filament_view_plugin.cc`.

## Verification and risk notes

- The lock is short-lived and protects only event-map bookkeeping; no rendering, material, camera, surface-order, or input behavior changes.
- A code audit plus `do_compile` proves the patch builds and every map access follows one synchronization rule. The ordinary QEMU run tests real callbacks, repeated frames, present, and screenshots. ThreadSanitizer would be useful for dynamic race detection, but do not mutate the production build's global CFLAGS or create another build/TMPDIR merely to instrument it; if the existing supported toolchain offers an isolated plugin TSan run without shared-state changes, record it as supplemental evidence.
- A stable process does not imply pixels. A positive LIT fixture does not imply production Sequoia. A QMP screenshot after process exit is not a live frame.
- This plan follows the official Yocto guidance that `devtool modify` applies existing recipe patches as Git commits and `devtool update-recipe` ignores uncommitted changes; project tooling then bounds the split-component baseline/rebase workflow.
